# Log Processor

The processor consumes raw log lines from Redis, converts them into a common
event shape, and stores the processed events in PostgreSQL. Redis is the
transport between the Generator and Processor; PostgreSQL is the persistent
destination.

## Processing flow

For each Redis Stream entry, the processor:

1. Reads the `raw_log` field from the `logs` stream.
2. Detects the source type from the raw text:
	- `sshd[` or `sudo:` -> `AUTH`
	- `process:` or `file:` -> `SERVER`
	- ` web:` -> `WEB`
	- `firewall:` -> `NETWORK`
3. Selects the parser from `PARSERS` and parses the line.
4. Calls `normalize_event` to add common fields and retain category-specific
	fields in `metadata`.
5. Inserts the normalized event into PostgreSQL's `events` table and commits
	the transaction.

Unrecognized source types, malformed lines, and parser errors are logged as
failures. The in-memory stream position is advanced only after successful
processing. The processor uses `XREAD`, not a Redis consumer group, and starts
at stream ID `0-0` each time it starts.

## Parsers

`PARSERS` maps the detected source type to the parser function:

| Source type | Parser | Log forms handled |
| --- | --- | --- |
| `AUTH` | `parse_auth_log` | Successful and failed SSH logins, logout, and sudo privilege changes |
| `SERVER` | `parse_server_log` | Process execution, process stop, and file access |
| `WEB` | `parse_web_app_log` | HTTP responses, including 200, 401, 403, 500, and 400 suspicious requests |
| `NETWORK` | `parse_network_log` | Allowed, blocked, port-access, and suspicious firewall connections |

Each parser returns a dictionary or `None`. A `None` result causes the
processor to reject the log rather than insert a partial event.

## Normalized events

Each accepted event contains:

| Field | Meaning |
| --- | --- |
| `event_id` | New UUID generated by the normalizer |
| `timestamp` | Parsed timestamp from the raw line |
| `source_id` | Source identifier supplied by the processor |
| `source_type` | `AUTH`, `SERVER`, `WEB`, or `NETWORK` |
| `host`, `user`, `src_ip`, `dst_ip` | Common values when present |
| `event_type` | Parser-determined event type |
| `severity` | Common severity value when present; current parsers do not set one |
| `message` | The original raw log line |
| `metadata` | Category-specific fields not in the common-field set, such as process, path, status, port, protocol, or reason |

The insert maps `user` to the database column `user_name` and serializes
`metadata` as JSON. The database insert writes the event ID, source, timestamp,
type, severity, user, IP addresses, host, message, and metadata to
`events`.

## Configuration

The processor reads these environment variables:

| Variable | Default / requirement | Use |
| --- | --- | --- |
| `REDIS_HOST` | `redis` | Redis hostname |
| `REDIS_PORT` | `6379` | Redis port |
| `REDIS_STREAM` | `logs` | Stream consumed by the processor |
| `DATABASE_URL` | Required | SQLAlchemy connection URL |

The current `main()` always passes the source ID `source_001` to the
normalizer. Because `events.source_id` references `log_sources.id`, a
corresponding `log_sources` row must exist before inserts can succeed. The
provided database initialization SQL creates roles but does not create this
log source.

## Running with Docker Compose

From the repository root, start the complete stack:

```powershell
docker compose up -d --build
```

Check service status and processor output:

```powershell
docker compose ps
docker compose logs -f processor
```

The Processor Dockerfile runs `python processor.py`. Compose supplies Redis at
`redis:6379`, consumes the `logs` stream, and supplies a PostgreSQL
`DATABASE_URL` using the Compose database variables. Compose startup ordering
does not itself wait for PostgreSQL or Redis readiness; the processor keeps
retrying its read loop, while database errors are logged per message.
